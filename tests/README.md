# Avenys modular language suite

`tests/mod.mire` is the active root for the executable integration suite. Each
directory is a language or integration family and is discovered recursively by
`owl test` through `owl.toml`.

Every execution deletes the previous contents of `tests/log/` and writes only
one directory per family under `tests/log/<family>/`, containing `count.json`
`log.json` and `info.json`. There are no loose JSON files and no historical
snapshots. `info.json` has the stable dashboard fields `RAM`, `CPU %`,
`Time ms`, `Total`, `Warns` and `CODES`.
Memory is measured as the peak RSS of each independent test process; family
metrics report their maximum observed test peak.
The JSON is generated by the compiler test command from the observed result;
there are no synthetic passing returns or retained results from an earlier run.
The runner measures child-process RSS and CPU directly, and associates warning
diagnostic names and compilation error codes with the family that produced
them. Mire source helpers cannot replace this measurement because they do not
own the child process or the compiler diagnostics.

Reproducible command from the repository root:

```text
owl test --log -j 8 --verbose

The suite resolves Mire and Kioto from `~/.owl/libs/`; local copies under the
workspace are development sources only and are not test dependencies.
```

Logging is opt-in. Without `--log`, tests execute without creating or
rotating `tests/log/`. The same flag is accepted by both `mire test` and Owl;
Owl forwards it to the compiler test runner.

The native fixtures are rebuilt with the compiler CLI when needed. Their
executable smoke tests live beside each artifact, so a successful link is not
mistaken for a successful runtime call:

```text
mire build ../kioto/code/mod.mire --artifact shared --output tests/libs/kioto/kioto.so
mire build ../kioto/code/mod.mire --artifact static --output tests/libs/kioto/kioto.a
mire build ../mire/code/mod.mire --artifact shared --output tests/libs/mire/mire.so
mire build ../mire/code/mod.mire --artifact static --output tests/libs/mire/mire.a
cp /usr/lib/libsqlite3.so tests/libs/sqlite/libsqlite3.so
cp tests/libs/sqlite/libsqlite3.so tests/libs/sqlite/libsqlite3.so.0
```

The corresponding native checks are:

- `tests/libs/kioto/tests/mod.mire`: calls `pal_cpu_count` from `kioto.so`.
- `tests/libs/mire/tests/mod.mire`: calls `mire_hash_u64` from `mire.so`.
- `tests/libs/sqlite/tests/mod.mire`: calls `sqlite3_libversion_number` from
  the copied SQLite shared object.
- `Integration/DynamicLibraries/mod.mire`: links both the Mire archive and
  Kioto shared object and executes one symbol from each artifact.

These checks are discovered by the main suite and included in its global
count.

## Known documented mismatch

The language documentation currently shows `box(value)` as an allocator
builtin. The active compiler does not register a `box` builtin, so the Box
family tests the supported `Box[T]` generic record construction and field
access instead of hiding the missing allocator behind a constant return. A
compiler regression for registering the documented allocator must be added
before changing that fixture to dereference a heap box.

The server is pinned to these fixture libraries through explicit `extern lib`
paths in `tests/log/web/src/server.mire`. Rebuild the Kioto and Mire fixtures
after changing either project; do not rely on `~/.owl/libs` for this test.
`libsqlite3.so` is the host SQLite shared library copied into the fixture tree
so the web binary carries an `$ORIGIN` runpath to `tests/libs`.

The optional Mire-only dashboard lives in `tests/log/web/`. The test runner
preserves that directory while rotating generated JSON. Run it directly from
that directory; its `owl.toml` already selects release mode, optimization,
cache and native dependencies:

```text
cd tests/log/web
owl run -j 6 src/server.mire --release -O 3
```

Open `http://127.0.0.1:18080/`. The WebSocket endpoint is `/ws`; the JSON
endpoint is `/api/logs`. Each start appends one global snapshot to
`tests/log/web/src/runs.sqlite3` using the local SQLite Mire library; JSON output
remains overwrite-only. Connection and console events are appended to
`tests/log/web/logs/connections.log`.

The interactive control client is started in another terminal from the same
directory:

```text
owl run -j 6 src/console.mire --release -O 3
```

Its commands are deliberately small and have no built-in help:

- `STOP` stops the server.
- `TRY GET /api/status` probes a fixed route and prints the response.
- `TRY GET /api/logs` probes the JSON endpoint.
- `TRY GET ../../` must return `403 Forbidden`; arbitrary paths are never
  translated into filesystem paths.
- `CHAT` reads the next console line as the name, records
  `127.0.0.1@EVE` for input `EVE`, and echoes a chat acknowledgement. The
  shorthand `CHAT EVE` is also accepted. Remote callers can set
  `X-Console-IP`; the value is logged as `ip@name` for traceability.
- `TRY CHAT Server` is the equivalent explicit probe form for the server user.

The server uses a Kioto async channel for connection events and a WebSocket
snapshot. The SQLite bridge uses prepared parameters and does not make SQLite
a Mire runtime dependency: the server links `libsqlite3` only because its
project manifest requests it.
